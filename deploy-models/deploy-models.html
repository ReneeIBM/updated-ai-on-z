Deploy Models

Before a model can be used in production, it often needs to be packaged, optimized, and prepared for its target runtime environment. This stage focuses on converting models into supported deployment formats, applying platform-specific optimizations, and preparing them for execution on IBM Z.

IBM Z supports multiple deployment paths based on the model type, deployment architecture, and target inference environment. Models developed with open source and commercial frameworks can be deployed using the same set of IBM Z deployment and serving technologies.

What happens at this stage?

Convert to a portable format

Export your trained model to ONNX (deep learning) or PMML (traditional ML) — standard interchange formats that work across Z operating systems and deployment tools.

Optimize for IBM Z hardware

Compile and quantize your model using the IBM Z Deep Learning Compiler or AI Optimizer to maximize inference performance on Telum and Spyre acceleration.

Move to production

Deploy your model to a production runtime — on z/OS, Linux on Z, or an OpenShift container environment — co-located with the enterprise data it needs to score.

Configure scoring endpoints

Set up the model to receive inference requests via REST API, CICS/IMS native scoring, batch jobs, or a gRPC serving endpoint.

Who is this stage for?

Optimization and deployment are jointly owned by ML Engineers and IT Architects. The ML Engineer handles model conversion, compilation, and the deployment artifact. The IT Architect owns the infrastructure decisions — operating environment, serving topology, and integration with business applications. Data Scientists are stakeholders who validate that the deployed model performs as expected.

Where to Start

Your path is determined by two things: your model type and your target accelerator. The three subsections below map to those two dimensions.

Deploying Traditional Machine Learning Models

Traditional ML models (classification, regression, recommendation, forecasting) are deployed via PMML and run on the Telum on-chip accelerator.

Export and deploy via PMML — Snap ML and scikit-learn

You have a model trained with Snap ML, scikit-learn, XGBoost, Spark MLlib, or another traditional ML framework and need to move it to production.

→ Export to PMML and deploy through MLz or the AI Toolkit scoring services. PMML provides a portable format that does not require the original training framework at inference time.

Common approach: Train with Snap ML or scikit-learn → Export to PMML → Deploy and score through MLz or AI Toolkit.

Note: Snap ML is primarily a training technology. Deployment begins after exporting. Snap ML can also be used within MLz or the AI Toolkit as part of a broader deployment pipeline.

Full lifecycle on z/OS — Machine Learning for IBM z/OS (MLz)

You want model registration, deployment, scoring endpoints, and lifecycle management fully integrated into the z/OS environment.

→ Use Machine Learning for IBM z/OS (MLz). MLz is the primary deployment and scoring platform for traditional ML models on z/OS, supporting PMML imports from any training tool and exposing REST and CICS/IMS native scoring endpoints.

Common approach: Build or import model (from any tool that exports PMML) → Register in MLz → Deploy as a scoring endpoint co-located with z/OS applications.

Deploying Deep Learning Models and Encoder LLMs (Telum On-Chip Accelerator)

Deep learning models and encoder LLMs share the same deployment path on IBM Z when targeting the Telum on-chip accelerator: convert to ONNX, compile with the IBM Z Deep Learning Compiler (zDLC), and deploy via a serving platform. Encoder LLMs can also choose the Spyre path — see the next subsection.

Standard deep learning path — ONNX + zDLC

You have a neural network trained with TensorFlow, PyTorch, or any other framework — including models trained externally with Keras or Hugging Face — and want to deploy it on the Telum on-chip accelerator.

→ Convert to ONNX, then compile with the IBM Z Deep Learning Compiler (zDLC). zDLC optimizes the ONNX model for IBM Z hardware, generating a deployment artifact that leverages Telum AI acceleration automatically.

Common approach: Export model to ONNX → Compile with zDLC → Deploy via IBM Z Accelerated for Triton Inference Server, MLz, or Red Hat OpenShift AI.

TensorFlow direct serving — TensorFlow SavedModel

Your model was built with TensorFlow and you want to skip ONNX conversion by deploying directly with TensorFlow Serving.

→ Export as a TensorFlow SavedModel and deploy with IBM Z Accelerated Serving for TensorFlow. This avoids the ONNX conversion step while still leveraging Telum hardware acceleration.

Common approach: Train with TensorFlow → Export SavedModel → Deploy to IBM Z Accelerated Serving for TensorFlow.

Note: The ONNX → zDLC path is also valid for TensorFlow models and gives access to Triton or RHOAI as serving platforms.

Multi-framework or containerized serving — Triton and Red Hat OpenShift AI

You need to serve multiple model types from a shared inference platform, or your team works in a containerized OpenShift environment.

→ Use IBM Z Accelerated for Triton Inference Server, optionally managed through Red Hat OpenShift AI. Triton supports TensorFlow, PyTorch, ONNX, and zDLC-compiled models from a single serving runtime.

Common approach: Convert model to ONNX and compile with zDLC → Deploy to Triton → Optionally manage deployment pipelines and monitoring through Red Hat OpenShift AI.

Encoder LLMs on Telum — ONNX conversion path

You have an encoder large language model (e.g., BERT-style) and want to run it on the Telum on-chip accelerator rather than Spyre.

→ Convert the encoder LLM to ONNX and follow the same deep learning path: compile with zDLC and deploy via Triton, MLz, or Red Hat OpenShift AI.

Common approach: Export encoder LLM to ONNX → Compile with zDLC → Deploy via Triton Inference Server or Red Hat OpenShift AI.

Note: Encoder LLMs can also be served on Spyre — see the next subsection. The choice depends on your SLOs and whether you have Spyre available.

Deploying Large Language Models on Spyre

Decoder LLMs always use Spyre. Encoder LLMs may also choose Spyre over the Telum on-chip accelerator depending on SLOs and hardware availability. The tools in this subsection are specific to Spyre-accelerated LLM workloads.

Decoder LLMs and encoder LLMs on Spyre — Red Hat AI Inference Server

You are deploying a decoder LLM (e.g., Llama, Granite) or an encoder LLM that you want to accelerate on the IBM Spyre Accelerator.

→ Use Red Hat AI Inference Server. This is the primary serving platform for LLMs that leverage Spyre on IBM Z. It is purpose-built for large model inference and is not used for traditional ML or deep learning models on the Telum accelerator.

Common approach: Source or fine-tune an LLM → Deploy via Red Hat AI Inference Server with Spyre acceleration on IBM Z.

LLM deployment with MLOps and multi-platform support — Red Hat OpenShift AI

You need MLOps pipeline management, model catalogs, and monitoring around your LLM deployment, or you want a single platform that covers both Telum and Spyre workloads.

→ Use Red Hat OpenShift AI. Unlike Red Hat AI Inference Server, OpenShift AI supports both Telum on-chip accelerator and Spyre workloads, making it the right platform when you need coverage across multiple model types or accelerators.

Common approach: Deploy LLMs through OpenShift AI using the Red Hat AI Inference Server runtime for Spyre workloads, or Triton for Telum workloads — all managed from a single MLOps platform.

Hybrid routing across platforms — AI Optimizer for Z and LinuxONE

You have a hybrid deployment that spans IBM Z and other platforms (cloud, GPU clusters), and you need intelligent routing of LLM inference requests to the most optimal platform.

→ Use AI Optimizer for Z and LinuxONE. AI Optimizer acts as a gateway that receives a prompt and routes it to the most optimal platform based on configured criteria — IBM Z Spyre, Telum, or an external GPU. It now includes Red Hat AI Inference Server as an integrated component.

Common approach: Deploy AI Optimizer as the inference gateway → Route LLM prompts to Spyre via the embedded Red Hat AI Inference Server or to an external GPU platform depending on the request.
