AI on IBM Z

Serve Model

Serving is the stage where a deployed model becomes accessible to applications and users — exposing predictions via a REST API, a gRPC endpoint, or a native z/OS scoring interface that an application calls in real time. On IBM Z, inference serving is where the performance story becomes concrete: co-locating the serving layer with your transactions and data eliminates network latency and makes in-transaction AI at enterprise scale possible.

IBM Z provides a range of serving options to match the model type, workload pattern, and application environment — from native CICS and IMS scoring inside z/OS to containerized multi-framework servers on Linux on Z to enterprise LLM inference for generative AI workloads.

What happens at this stage?

Expose a scoring endpoint

Make the deployed model accessible via a REST API, gRPC interface, or native z/OS scoring call that applications can invoke for real-time predictions.

Handle production traffic

Configure dynamic batching, concurrency, and throughput settings to serve inference requests at production volume while meeting SLA requirements.

Manage model versions

Support hot model reload and versioned endpoints so you can update or roll back models without downtime.

Infuse AI into applications

Integrate the serving endpoint directly into business applications — CICS transactions, IMS workflows, microservices, or REST-based integrations.

IBM Z inference performance

Co-locating your serving layer with applications and data on IBM Z eliminates the round-trip to a remote inference server. IBM internal benchmarks on z16 showed 20x lower response time and 19x higher throughput versus a compared x86 server with 60ms network latency — and 41x less energy per inference operation versus an NVIDIA GPU. On IBM z17, Telum II can process up to 450 billion inference operations per day with 1ms response time.

Who is this stage for?

Serving is primarily owned by ML Engineers and Application Architects, with Data Scientists as stakeholders validating that the serving layer produces correct outputs. Line of Business and IT Architects set the SLA and throughput requirements the serving layer must meet.

Where to Start

Your serving choice depends on the model type, where you deployed, and how your application will consume predictions. Use this to find your path:

Serving TensorFlow models on Linux on Z

Your model is a TensorFlow SavedModel and you need a production-grade REST or gRPC endpoint with version management and Telum acceleration.

→ Use IBM Z Accelerated Serving for TensorFlow. A flexible, high-performing serving system for TensorFlow models, served via HTTP REST or gRPC, with Telum II acceleration on z17.

Serving multiple frameworks or model types

You have a mix of model types — ONNX, SnapML, PyTorch — or need a unified serving platform that handles ensembles and concurrent models.

→ Use IBM Z Accelerated for Triton Inference Server. A multi-framework, high-performance inference server supporting SnapML, ONNX/DLC, and PyTorch backends — with dynamic batching and model ensemble support on Linux on Z.

Serving LLMs and foundation models

You're serving a large language model — Granite, Llama, Mixtral, or similar — for generative AI use cases on IBM z17 with Spyre or Telum II acceleration.

→ Build or fine-tune models in watsonx.ai, then serve them using Red Hat AI Inference Server (vLLM-based), Red Hat OpenShift AI, or AI Optimizer for IBM Z and LinuxONE depending on your deployment architecture.

Serving inside z/OS applications

Your application runs in CICS, IMS, or batch on z/OS and you need the model score to be part of the transaction — not a round-trip to an external server.

→ Use Machine Learning for IBM z/OS (MLz). Native CICS, IMS, and Java scoring services embedded in z/OS transactions, with near-zero latency and Telum acceleration.

Machine Learning for IBM z/OS — Native Scoring

For applications running on z/OS, Machine Learning for IBM z/OS provides native in-transaction scoring that doesn't require a separate serving layer. Models score directly inside CICS transactions, IMS workflows, and batch jobs — on the same system as the application and data, with near-zero latency. This is the serving pattern that enables 100% AI scoring of transactions in real time without SLA impact.

Native scoring interfaces

  • CICS native scoring — Score models directly inside CICS transactions; AI result available within the same transaction context
  • IMS native scoring — Integrate model scoring into IMS message processing workflows
  • Batch scoring — Large-scale batch inference for offline processing and overnight scoring jobs
  • REST API — Standard HTTP REST endpoint for applications that prefer a service-oriented integration pattern
  • WOLA (WebSphere Optimized Local Adapter) — Low-latency Java integration for JVM-based z/OS applications

Explainability at serve time

MLz provides continuous monitoring and explainability for scored transactions — supporting LIME and SHAP algorithms at the individual transaction level. Drift detection monitors both output drift and feature drift, enabling data scientists to identify when model behavior diverges from training.
