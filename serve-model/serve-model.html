Serve Model

Serving is the stage where deployed models are made available for production use. This includes running inference workloads, processing incoming requests, and returning model outputs to applications, services, and business processes. On IBM Z, serving can be performed close to enterprise data and transactional workloads, reducing data movement and enabling AI to be integrated directly into operational workflows.

IBM Z provides serving options for multiple model types. Traditional machine learning and deep learning models can leverage the Telum on-chip AI accelerator for real-time inference. Foundation models and large language models can be served using either the Telum on-chip AI accelerator or the IBM Spyre Accelerator, depending on the model architecture, deployment requirements, and runtime environment.

What happens at this stage?

Expose a scoring endpoint

Make the deployed model accessible via a REST API or native z/OS scoring call that applications can invoke for real-time predictions.

Handle production traffic

Configure dynamic batching, concurrency, and throughput settings to serve inference requests at production volume while meeting SLA requirements.

Manage model versions

Support model versioning and controlled updates, allowing new model versions to be deployed, tested, and rolled back with minimal disruption to production workloads.

Infuse AI into applications

Integrate the serving endpoint directly into business applications — CICS transactions, IMS workflows, microservices, or REST-based integrations.

Who is this stage for?

Serving is primarily owned by ML Engineers and Application Architects, with Data Scientists as stakeholders validating that the serving layer produces correct outputs. Line of Business and IT Architects set the SLA and throughput requirements the serving layer should meet.

Where to Start

Your serving platform is determined by your model type and target accelerator. The three subsections below map to those two dimensions.

Serving Traditional Machine Learning Models

Traditional ML models run on the Telum on-chip accelerator and are served through z/OS-native scoring interfaces or the AI Toolkit.

Your core applications run on z/OS and you need inference integrated directly with CICS transactions, IMS workflows, or REST calls — without containerization.

→ Use Machine Learning for IBM z/OS (MLz). MLz is the primary serving platform for traditional ML on z/OS, exposing REST and CICS/IMS native scoring endpoints co-located with your enterprise applications and data.

Common approach: Register PMML model in MLz → Expose scoring endpoint → Call from CICS transactions or REST-based application workflows.

Serving Deep Learning Models and Encoder LLMs (Telum On-Chip Accelerator)

Deep learning models and encoder LLMs targeting the Telum on-chip accelerator are served through containerized inference runtimes on Linux on Z or Z Container Extension. Encoder LLMs may also choose the Spyre path — see the next subsection.

You need a single inference server that handles ONNX, TensorFlow, PyTorch, and zDLC-compiled models, running in containers on Linux on Z or Z Container Extension.

→ Use IBM Z Accelerated for Triton Inference Server. Triton provides a unified, high-performance serving runtime for deep learning and encoder LLM models on the Telum on-chip accelerator.

Common approach: Deploy zDLC-compiled ONNX model to Triton → Expose gRPC or REST inference endpoint → Integrate with applications.

Your model is a TensorFlow SavedModel and you want a dedicated TensorFlow runtime without Triton.

→ Use IBM Z Accelerated Serving for TensorFlow. Provides a production TensorFlow Serving runtime optimized for IBM Z hardware, leveraging Telum AI acceleration.

Common approach: Export TensorFlow SavedModel → Deploy to TensorFlow Serving → Expose inference endpoint for application calls.

Multiple teams need shared serving infrastructure, monitoring, scaling controls, and pipeline management for deep learning workloads.

→ Use Red Hat OpenShift AI. OpenShift AI manages serving infrastructure for both Telum and Spyre workloads, making it the right platform when you need coverage across multiple accelerators or model types.

Common approach: Deploy model servers (Triton or TensorFlow Serving) through OpenShift AI → Monitor performance and scale inference workloads from a unified MLOps platform.

You have an encoder LLM (e.g., BERT-style) and want to serve it on the Telum on-chip accelerator.

→ Use IBM Z Accelerated for Triton Inference Server or Red Hat OpenShift AI. Encoder LLMs targeting Telum follow the ONNX → zDLC compilation path: export the model to ONNX, compile with IBM Z Deep Learning Compiler (zDLC), and serve via Triton or through OpenShift AI.

Common approach: Export encoder LLM to ONNX → Compile with zDLC → Deploy to IBM Z Accelerated for Triton Inference Server → Serve via gRPC or REST endpoint.

Note: Encoder LLMs can also be served on Spyre — see the next subsection. The choice depends on your SLOs and whether you have Spyre available.

Serving Large Language Models on Spyre

Decoder LLMs always use the IBM Spyre Accelerator. Encoder LLMs may also choose Spyre over Telum depending on SLOs and hardware availability. The tools in this subsection are specific to Spyre-accelerated LLM inference.

You need MLOps pipeline management, monitoring, and model governance around your LLM serving, or a single platform that covers both Telum and Spyre workloads.

→ Use Red Hat OpenShift AI. Unlike Red Hat AI Inference Server, OpenShift AI supports both Telum on-chip accelerator and Spyre workloads — making it the right platform when you need unified management across multiple model types or accelerators.

Common approach: Manage LLM serving through OpenShift AI using the Red Hat AI Inference Server runtime for Spyre workloads, or Triton for Telum workloads — all from a single MLOps platform.

You have a hybrid environment spanning IBM Z and other platforms (cloud, GPU clusters) and need intelligent routing of LLM inference requests to the most optimal platform.

→ Use AI Optimizer for IBM Z and LinuxONE. AI Optimizer acts as an inference gateway that receives a prompt and routes it to the most optimal platform — IBM Z Spyre, Telum, or an external GPU — based on configured criteria. It now includes Red Hat AI Inference Server as an integrated component.

Common approach: Deploy AI Optimizer as the inference gateway → Route LLM prompts to Spyre via the embedded Red Hat AI Inference Server, or to an external GPU platform, depending on the request and routing policy.
